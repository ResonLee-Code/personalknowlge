## V1.3.3（2026-10-19）

主题：**继续把纵向空间还给正文，并补上全屏时的窗口控制入口**。纯修复 / 布局版，不改数据结构。

### 标题区与底部信息区再压缩（2026-10-19 第二轮）

- **标签不再独占一行**：并进元信息行；未编辑时只是一个「+ 标签」，点开才出现输入框，
  失焦且没输入时自动收回；
- **标题区收紧**：标题输入 36 → 32px，行距与内边距各收一档；
- **底部默认收成一行摘要（32px）**：显示「关系 出 N · 入 N」「反向链接 N」「未解析 N」，
  右侧一个「展开 / 收起」；点「未解析 N」会**一次**展开整块并滚到未解析列表；
- 展开后仍受 **42% 限高 + 内部滚动**约束，原有关系 / 反向链接操作一个不少。

**实测（E2E，1280×800）**：标题+元信息 **90px**、底部摘要 **32px**、正文编辑区 **552px**。
**真机（1280×800，AX 坐标）**：底部信息区（含状态栏）**167 → 54px**；按同一口径，
正文可见高度从 **371 → 约 519px**（+148px，约 +40%）。

### 全屏时的窗口控制：鼠标扫过顶部即显示

问题：macOS 全屏后标题栏与红黄绿按钮被系统藏起；本机实测**鼠标移到顶部不会唤出**，
只有按 Esc 退出全屏才看得到（Codex 桌面端同样如此）。

处理：全屏时在窗口顶部放一条 **10px 悬停感应带**，鼠标扫过就淡入一个浮动胶囊：
红 / 黄 / 绿三个按钮（关闭、最小化、退出全屏）+「全屏」提示；移开 600ms 自动收起。
非全屏不渲染，仍用系统原生标题栏。真机验证：全屏 `1512×949` → 点绿色按钮 →
窗口恢复 `1380×859`，菜单栏与原生红黄绿按钮回来。

**验证**：前端 71 文件 / 380 用例（新增全屏控制条 3 条、行内标签 3 条）；E2E 主流程通过
（新增：默认摘要 < 60px、标题区 < 100px、展开后仍 ≤ 340px）。

## V1.3.2（2026-10-19）

主题：**非全屏窗口下把纵向空间还给正文**。这是一次纯修复版，不新增功能、不改数据结构。

### 非全屏窗口：正文编辑 / 预览不再被底部信息区挤没（2026-10-19）

**症状**（用户报的）：窗口不是全屏时，正文编辑/预览只剩两百多像素——上下被"标题 + 元信息"与
"关系 / 反向链接 / 本篇未解析链接"夹住，其中**本篇未解析链接**（9 条、每条一行 + 创建按钮）
一条就能吃掉半个窗口。

**修复**：

- 底部信息区（关系 + 反向链接 + 未解析）整体**限高 42%、内部滚动**——正文（上方 flex-1）始终拿得住空间；
- 「本篇未解析链接」默认**收起**，标题上保留数量徽标（`▸ 本篇未解析链接 9`），要看再点开；
- 标题 + 元信息区内外边距各收一档。

**实测**（1280×800 非全屏真机，同一篇有 9 条未解析链接的笔记，窗口位置同为 120,80）：

| 版本 / 状态 | 正文编辑区可见高度 | 底部信息区高度 |
| --- | ---: | ---: |
| V1.3.1（未解析常驻展开） | 204 px | 322 px |
| **V1.3.2 默认（未解析收起）** | **371 px** | **167 px** |
| V1.3.2 展开未解析（9 条） | 232 px（底部自己滚动） | 306 px（≈ 42% 封顶） |

正文可见高度 **+167 px（+82%）**，底部信息区 **−155 px（−48%）**。
在更小的 1024×700 窗口下，默认状态正文仍有 **258 px**；工具栏自动收成图标，不参与纵向挤压。

**验证**：E2E 新增断言（1280×800 下正文高度 > 220、底部 ≤ 340）；`BacklinkPanel` 单测改为
"先展开再操作未解析链接"；本机 `.app` 真机用 AX 坐标复核（窗口 1280×800 / 1024×700）。

### 发版流水线：校验文件统一 LF（2026-10-19）

V1.3.1 发布后抽验发现 `SHA256SUMS-windows.txt` 与 `SHA256SUMS-all.txt` 是 CRLF 行尾：
在 macOS / Linux 上 `shasum -c` 会把 `\r` 当成文件名的一部分，报 `No such file or directory`。
哈希值本身正确，只是校验文件自己过不了自己。

- Windows 作业改为**显式写 LF、无 BOM**（不再用默认 CRLF 的 `Out-File`）；
- Release 汇总步骤再 `tr -d '\r'` 兜底；
- 已重新上传 V1.3.1 Release 的两份校验文件（文件名、哈希值不变），重新下载后 **6/6 OK**。

V1.3.1 的完整抽验记录见 [ACCEPTANCE_V1.3.1.md](./ACCEPTANCE_V1.3.1.md) §C。

### 界面梳理：去掉重复入口、开关归位、区块可折叠、截断不再"空一块"（2026-10-15）

一轮把"同一个动作有多个入口"和"控件离它管的东西很远"的地方收干净：

- **侧边栏开关只剩一个，而且不跳位置**：删掉顶栏的「切换侧边栏」（与侧边栏自己的收起 / 展开重复）；
  收起后 44px 图标栏里的「展开」从顶部挪到**底部那一行**，与展开态底栏的「收起」同高——
  两个状态下开关停在同一个位置，点它不用重新找；
- **收起后的侧边栏变成图标栏**（对 Codex 桌面端）：导航项一个个摆进去，选中项品牌色底、
  悬停出名字，点图标直接切页面。以前收起后只剩「新建笔记」——**收起不等于失去导航**；
  两态共用一份 `navItems.ts` 定义（免得两处对不上）。
  实现上有个坑记一笔：`TooltipTrigger asChild` 合并 props 时会把**函数形式的 `className`**
  拼成字符串（实测 class 里真出现了函数源码，选中高亮整条失效），所以图标栏的高亮用
  **纯字符串 className + `aria-[current=page]:` 属性变体**；
- **大纲开关挪到笔记列表栏的头部**：原来在编辑器工具栏，但那个工具栏只在打开笔记时才存在，
  而列表栏一直都在。现在栏头是 `标题 + 篇数`（篇数紧贴标题，一眼看出"这是哪个范围的几篇"）
  加最右边的「大纲」开关；没选中笔记时开关置灰。
  随之把右侧大纲形态（常驻 / 贴边 / 隐藏）从编辑器的局部状态提到 `uiStore`——列表栏也要能开这一列。
  注意一个连带变化：**这一栏显示大纲时，栏头归大纲**（有「〈〈 返回列表」），开关随之让位，
  回来走那个按钮（E2E 两处按新口径改了）；
- **删掉侧边栏的「设置」导航项**：右上角那个是唯一入口（顶级动作不该有两个入口）；
- **分类 / 标签区块可折叠**：点区块标题折叠 / 展开（带 `aria-expanded`），分类多了不再把侧边栏顶长；
  折叠是内存态（与侧边栏折叠同口径，不写设置）；
- **标题被截断时，条目右侧的「新建子文档」「更多操作」常显**：这两个按钮一直占着位置（平时只是透明），
  标题一长就被截断，而按钮在 hover 之前看不见——屏幕上表现为"标题没显示全、右边却空着一块"。
  现在截断就把按钮显出来（未截断的条目仍保持 hover 才出现的安静样子）；
- **根因是个布局缺陷**：Radix `ScrollArea` 在 Viewport 里塞了一层 `display: table; min-width: 100%`
  的内容 div，table 盒子按**内容**撑宽——实测面板 320px 时条目行有 520px，于是标题永远不截断、
  行右侧的按钮被面板裁掉（"标题被面板边缘切掉，右边什么都没有"）。
  已在 `src/components/ui/scroll-area.tsx` 用 `[&>div]:!block` 覆盖掉那层 table（内联样式必须用 `!`）。

**验证**：`e2e/app.spec.ts` 新增步骤 35（侧边栏开关同高、分类 / 标签折叠、侧边栏没有设置项、
列表栏头部的计数与开关位置、长标题行按钮常显、没选中笔记时开关置灰）；
`NoteListItem.test.tsx`（截断 / 未截断两态）、`OutlineToggleButton.test.tsx`、`uiStore.test.ts` 补了单元覆盖。

### 修复：插入菜单里的「图片…／附件…」点了没反应（2026-10-18）

**症状**（用户实测报的）：点「＋ 插入内容 → 图片…」，什么都不发生——连系统文件选择框都不弹。

**根因**：上一轮重写编辑器工具栏那段 JSX 时，把菜单用来触发文件选择的隐藏
`<input type="file">` **一起删掉了**（`attachInputRef.current` 永远是 null）。
这是重构夹带删除 —— 菜单项、`pickAttachment`、附件保存链路都还在，唯独"弹框"那一步断了。

**修复**：把 input 放回工具栏（带 `data-testid="insert-file-input"`，并写清为什么不能动它）。

**验证**（这回是端到端，不是"看起来对"）：

- `pnpm test:e2e` 新增断言：点「图片…」必须**真的触发 file chooser**（`waitForEvent('filechooser')`）；
  浏览器预览模式写不了本地文件，所以紧接着必须出现**明确的失败提示**「保存图片失败」——
  静默无反应视为失败；
- 真机验收新增**第 13 条**：从菜单点「图片…」→ 系统「打开」面板（⌘⇧G 输路径 → 回车 ×2）→
  选完图后断言 **`attachments/`（含子目录）里出现这一轮新生成的 `.png`**，且笔记正文里
  写入了含 `attachments/` 的 Markdown 链接。

**插入菜单清单审计**（对照语雀的插入面板）：

| 语雀有 | 我们 | 说明 |
| --- | --- | --- |
| 图片 / 表格 / 附件 / 待办 / 代码块 / 公式 / 流程图 / 时序图 / UML 图 / 思维导图 / 引用 / 分割线 / 日期 | ✅ 都有 | 图片与附件走本机附件流程（落 `attachments/`，正文插相对路径） |
| 画板、数据表、画册、看板、状态、AI 助手、折叠块 | ✗ 有意不做 | 这些是语雀**私有块**，没有 Markdown 对应物——硬做出来会变成"离开本应用就失效"的内容，违背本项目"正文就是普通 Markdown"的口径。折叠块用 `<details>` 也不行：预览按标准 Markdown 渲染、不执行内联 HTML |

**验收脚手架补强**（这轮真机跑暴露的）：

- 新增 `focus` 原语：Radix 的下拉菜单触发按钮**只认 `pointerdown`**，`AXPress` 合成的 `click`
  打不开它（工作区切换、插入菜单、更多操作都这样）。现在"聚焦触发按钮 → 回车"就能展开
  （这也是键盘用户的真实路径），菜单项会以 `AXMenuItem` 出现；
- `check` 的 `containsFile` 改为**递归**查找（最多 3 层）：附件按 `attachments/YYYY-MM/` 分月存放，
  只读顶层会得出"没有 .png"的假失败。

- **文本格式条**：改成由**实测宽度**决定"能放几个按钮"——按钮按优先级从左到右依次排列、
  **始终靠右**，放不下的才进「…」（全都放得下时不显示「…」）。与左边的「保存」之间留
  **硬间隔**（两个保存按钮宽，约 132px），格式条不会越过它。实测：窗口 1600 宽时 16 个全铺开、
  1440 宽时 13 个 + 「…」、1100 宽时 1 个 + 「…」；
- **设置页改回单列铺满**：上次改成"一次只显示一节"之后，之前那套多列瀑布流就变成坑了——
  窗口跨过 xl/2xl 时会分列，而当前这一节往往只有一张卡片，于是卡片被塞进半列、右边空一片
  （现象就是**窗口越宽、设置内容反而越窄**）。现在一列到底、卡片占满右栏（与 Codex 设置页一致）。

- **收藏 / 移动分类 / 更多操作移到顶栏**（用户附图 1）：三者在**打开着笔记时**出现在顶栏右端，
  与「已同步」同一行；「已同步」也**紧挨搜索栏**，搜索栏 + 已同步整体左移（以前搜索框居中、
  保存状态贴在最右，中间空一大段）。实现上顶栏只发**动作请求**（`uiStore.requestNoteAction`），
  对话框仍挂在编辑器里消费（它们要用 note / navigate / 各对话框自己的状态）——
  顺带把「对话框开关」也改成由请求派生，避免在 effect 里 setState（React 的 lint 规则拦这个）；
- **文本格式条并进编辑器工具栏同一行、靠右**（用户附图 3/4）：第二行整行撤掉，编辑区上移；
  宽度不够时由格式条自己的「…」菜单兜住（常用几个直接显示，标题 / 分割线 / 缩进等收进菜单）；
- **设置页右侧铺满**（用户附图 3）：去掉 `max-w-3xl` 限宽，分节标题（卡片外）与卡片行占满右栏。

**验证**：`pnpm test` 69 文件 / 374 用例；`pnpm test:e2e` 新增断言——顶栏里有
`favorite-toggle` / 移动分类 / 更多操作，且与「已同步」同一行、「已同步」在搜索栏右侧；
格式条与插入菜单在**同一行**、第二行不再存在、"更多格式"菜单在；设置页右侧宽度铺满
（`main` 宽 − 导航宽 − 40 之内）。真机验收随包重跑。

### 检索命中能跳回原文精确区间（Track D1 / N5）

- 搜索命中新增 `location`（`{ heading, charStart, charEnd }`）：点结果会**跳进编辑器、

- 区间口径统一为**码点下标**（与后端同一坐标系），前端在 `src/lib/highlightRange.ts`
  显式换算成 CodeMirror 的 UTF-16 下标——含 emoji 时直接相加会错位，有单测钉住；
- **老库升级**：出现过「有笔记索引、没有分块」时，打开工作区会判定索引落后并**自动重建**一次，
  不会出现"能搜到但跳不准"的静默失效；
- 1 万篇基准复测：检索 **p95 50.2 ms**（红线 200 ms）、召回 100%，未退化；
  代价是扫描/重建多算一遍分块（1 万篇扫描 4.84s，比之前约慢 1s）。

### 决策层骨架：引擎 + 缓存 + Trace（Track D2 / N6）

- 打分统一走**决策引擎**（`DecisionEngine`）：先查缓存 → 按候选链逐档试 → 写缓存并记 Trace；
  「哪一档可用」仍由既有闸门算好传入，引擎自己不做外发判断；
- **决策缓存**（迁移 012，`decision_cache` 表）的键是**内容寻址**的：
  `kind + 查询 + 每个候选的 (id/标题/片段/时效) + 候选链的档位`。因此
  **材料一变就不命中**、**用户开关模型后不会命中旧档位的结果**；另有 TTL（10 分钟）兜底，
  过期或坏数据一律当作没有并顺手删掉；
- **每次打分都留下可解释 Trace**：报告新增 `decisionTrace`
  （`{ kind, cache: hit|miss, provider, candidates, attempts[], tookMs }`），
  界面在报告头部显示「决策 rule · 现算 · 试过 local.ollama✗ → rule✓」这样的摘要；
  只记元数据（档位 / 条数 / 原因），**不含正文**；
- 实测收益：同一批材料在**同一工作区里重复判定**不再重复调模型
  （集成测试：第二次 `cache: hit`，且桩模型的调用次数不增加）。

### 检索通道化 + 融合框架（Track D3 / N7 第一步）

- 检索从"直接查 FTS"升级为**多通道 + 融合**：新增 `Retriever` 实现
  （目前是 `bm25` 通道，把现有 FTS 包起来，**关键词检索永远可用**）与
  **RRF（Reciprocal Rank Fusion）**：`score = Σ 1/(k + rank)`，按名次融合不同量纲的通道；
- 同一条分块被多个通道召回时**并成一条并标注来源**（`providers`），
  所以"这条是谁召回的"永远说得清；
- **单个通道不可用/出错不影响整次检索**：只如实标注（`channels[].available/note`），
  其它通道照常——这就是"检索永远可用"的落地方式；
- 命中带 **D1 的原文精确区间**（`charStart/charEnd` + `heading` + `chunkIndex`）；
- 新命令 `ai_retrieval_search`（返回通道状态 + 融合命中）。**本步不引入任何外发**；
  向量档（在线嵌入）是下一步，未构建时 `vector` 通道如实标"不可用"并跳过。

### 向量检索：在线嵌入 + 增量构建（Track D3 / N7 第二步·第三步）

- 新增**向量通道**（迁移 013 的 `chunk_embeddings` 表 + `vector_index`）：把每个分块向量化后
  存**本地**，检索时全量余弦取 top-k 再与 BM25 融合（RRF）。**向量本身不出机器**，
  只有构建时把片段文本发出去一次；
- 嵌入复用**在线模型的地址与 Key**，但**模型名单独一项**（嵌入模型通常与聊天模型不同）；
  开关与参考口径默认关闭，地址只接受 https 公网域名（本机可写 localhost）；
- **构建是显式确认的一次性动作**：点「构建向量索引」先弹确认框，写明
  **目标主机 / 涉及篇数与分块数 / 本次实际外发多少片段**；构建期间推
  `ai://vector-index-progress` 进度事件，界面显示"已嵌 N / M"；
- **增量**：分块内容指纹没变就不重嵌（只有改过的笔记会重发）；
- **检索永远可用**：向量档没开/没授权/没构建/出错时，`channels` 里如实标不可用并跳过，
  关键词检索照常；授权与地址/模型联动（换地址或换嵌入模型 → 授权作废）；
- 新命令：`ai_vector_index_status` / `ai_vector_index_preview` / `ai_vector_index_build` /
  `ai_vector_index_clear`；「设置 → AI → 向量检索」有完整入口（含确认框与进度）。

### 决策模型档：Jev / Perplexity Decisions（Track D4 / N8 起步）

- 「设置 → AI → 决策模型」新增**可选档位**：规则档（默认，离线、不联网）或 **System One**
  ——**TypeSafe Jev 与 Perplexity Decisions 协议完全相同**，内置两套预设

  一个下拉即可切换；
- 决策档**排在最前**：配好并授权后，研究打分会先问它（类型化输出 + 校准置信度），
  失败自动降级到在线聊天模型 → 本地模型 → 规则档，流程永不中断；
- 参数照抄官方文档：一次请求最多 128 个问题（我们按 120 分批）、`score` 用**有序档位数组**、

- 新命令 **`ai_decision_probe`**（契约探针）：用**我们自己的中文题**跑出
  **准确率 / 自洽性 P(A)+P(¬A) / 两次一致性 / 矛盾判别 / 耗时 / 输入 token / 估算成本**，

  429 = 限流"这类提示从未生效——现在统一改为按状态码自行解释。

> 实测（2026-10-13，经本机代理调真实 Perplexity）：中文材料上相关项
> `score 0.997 / confidence 0.994 → Use`、无关项 `score 0.011 → Drop`；

- 探针报告与界面都显示 ECE / Brier / 折外 ECE / 分箱（"说多少 vs 实际对多少"）。

> **真机实测（2026-10-13，27 题，两次请求）**：准确率 **27/27 = 100%**（含上述全部弱项），

> **题库已补上"材料里没有答案"那一族（2026-10-13 第二轮，共 47 题）**：
> 20 道题问的是**材料之外、只有我们知道真相**的私事（本机 python 版本、代理端口、
> 仓库文件名、schema 版本…），每题正反两问 → 真实正例率恰好 50%。
> **真机实测**：总准确率 **38/47 = 80.9%**、**ECE 0.1193**（线 0.05）、折外 0.1668、

> "材料外"题 **13/20**，概率散落在 0.1–0.7，平均说 **0.51**（理想 0.5）。
> **这说明两件事**：① 它**不会**对材料里没有的东西硬撑 0.99（好事）；
> ② 但它的"不确定"**只有弱信息量**（ECE 0.12 高于 0.05 线，且 0.2–0.4 段欠自信、

> **真机实测**：
>
> | 族 | 准确率 | ECE | 平均陈述概率 |
> | --- | --- | --- | --- |
> | 材料内（能推出来） | **40/40 = 100%** | **0.0159**（线 0.05 内） | — |

> **结论**：① 凡是**能从材料推出来**的，它答对且基本不吹（ECE 0.016）；
> ② 对**材料没有**的东西，它**偏"说没有"**（平均 0.376，且 0.2–0.6 段实际正确率普遍高于陈述值）——

### 守卫：`cp` 回写历史快照会触发冲突保护（B1 受控复现）

- V1.2.1 真机验收那晚出现的「保存失败」当时只是**推测**（"我正用 `cp` 把版本历史写回文件"）。

### 真机验收脚本：AX 那一层真的跑起来了（Track E1）

`scripts/acceptance/` 早就写好了，但**从没在真机上跑过**——之前只有
"能加载、`--preflight` 会报权限"这一级证据。这次补上真跑，第一次就暴露了 **4 个脚手架自身的缺陷**
（不是应用的问题，但每一个都会让结论表**说谎**）：

1. **AX 读取全程失效**：JXA 里属性名不桥接成 `CFString` 会返回 `-25201`；
   桥接之后错误码变 0，但 `Ref()` 拿到的仍是**不可解引用**的对象——
   于是整棵树被读成"一个节点"，屏幕上明明有的按钮全部"没找到元素"。改走 `System Events` 读树后，
   WKWebView 里的完整界面树（含 React 组件）都能读到；
2. **没有"现场准备"**：应用停在欢迎页时，后面每条用例的第一次点击必然落空，
   报告写成"6 条失败"——把**现场没准备好**说成**功能有问题**。这正是本项目最忌讳的谎报。
   现在真跑前自己摆现场：切前台 → 按 Esc 清残留弹层 → 确认目标工作区已打开
   （欢迎页按「最近打开」里的**路径**点开；全新机器则自动新建）；**摆不好就中止、不出结论表**，
   与 `--preflight` 同一条纪律；
3. **无障碍树会被 WebKit 收起来**：没有 AX 客户端持续轮询时，树里只剩窗口边框那三个按钮。
   真跑期间由 `lib/ax-keepalive.js` 保活轮询；
4. **坐标点击在这个 WebView 里不生效**（补 `kCGMouseEventClickState`、按下/抬起之间加间隔都没用），
   而 `AXPress` 有效——按钮、链接、**输入框**都能点（输入框会被正确聚焦）；
   另外中文用 `keystroke` 会进系统输入法候选窗（屏幕上冒出一排「啊啊啊…」），
   改走**剪贴板 + ⌘V**，中英文都稳。
5. **`mac.click` 漏传应用名**：代理侧按名字找不到进程 → "查元素"永远失败 →
   每次点击都**静默退化成"按坐标点"**（步骤照样报 ✅，因为点击本身成功返回）。
   这条是修完前 4 条才暴露的：修好后 15 次点击**全部走 `AXPress`、0 次坐标兜底**。
   教训：**"步骤通过"不等于"动作生效"**——所以每条用例都配了文件级 / 元素级断言。

### 附件：「未引用」判定补上「只写文件名」的写法（Track F3）

附件页一直有「未引用」标记，但判定只认正文里带 `attachments/` 的路径。
后果很隐蔽：用户按 Obsidian 习惯写 `![[20261014-004146-图-01m4v2.png]]`（**只写文件名**）时，
这张图会被标成「未引用」——**下一次清理就会删掉还在用的图**。

- **判定口径正式写进** [API_CONTRACT.md](./API_CONTRACT.md)（四种写法逐条列出）：
  相对路径（应用自己写入的 `../attachments/…`）、`[[带路径]]`、`[[完整文件名]]`、普通 markdown 链接；
- 现在**只写文件名也认**（wikilink 与 `[文字](文件名)` 都认），匹配按**完整文件名精确匹配**；
  同名附件无法区分时**全部**算被引用——**保守方向**：宁可漏报孤儿，也不能误删在用的文件；
- 明确**不算引用**的一种情况：写用户**最初的文件名**（如 `![[图.png]]`）。
  附件落盘会被重命名成 `<时间戳>-<名字>-<短id>.<扩展名>`，那条链接指向的文件并不存在、
  预览里也打不开（**悬空引用**）——把它算成"被引用"只会让真正没人用的文件永远清不掉；
- 附件页新增「**只看未引用（N 个 · X MB）**」筛选（再点一次恢复全部），清理时一眼看到该处理哪些；
  删除仍是逐条二次确认（引用会失效时确认框会列出来）；
- 测试：Rust 4 条（`tests/attachment_admin_flow.rs`，含四种写法的口径守卫、悬空引用不算引用；
  反向验证过——把"只写文件名"的识别短路掉，用例立刻失败）+ 前端筛选用例。

> 只做**识别与呈现**，没有新增"一键批量删除"：删除用户文件是不可逆动作，
> 当前仍是**逐条确认**；要不要批量清理由你定。

### 失败原因"点得开"了（Track F2）

B3 已经让失败原因**可见**（不再只挂悬停提示）并写进应用日志，但还有两件事挡着用户看清：
**头部空间有限、长原因被截断**，而**toast 提示会自己消失**——想回头看时已经没了。

- 新增统一组件 `FailureDetail`：一行摘要 + 「**详情**」按钮，点开是**完整原文**（不截断），
  可以带**错误码**与补充信息（文件路径等），底部一键**复制详情**（直接贴进报障）；
  剪贴板不可用时不会报错——不把"复制失败"变成新的失败源；
- 新增统一入口 `reportFailure()`：所有失败提示都走它——**标题只放摘要**（长文本不再被挤断）、
  **完整原因放 `description`**、停留时间放长到 8 秒、带「复制详情」；成功路径仍走 `reportAction()`；
- 编辑器头部的「保存失败」徽标接上 `FailureDetail`：以前被截断的那半截原因，现在点得开；
- **全仓 30+ 处失败路径一次性统一**（设置页的备份 / 校验 / 恢复 / 导出 / 扫描 / 打开目录、
  AI 设置的自检 / 向量预览 / 向量更新 / 决策探针 / 审计读取、图谱导出、导出对话框、
  附件删除、历史版本（还原 / 保存 / 命名 / 删除）、关系增删、笔记新建 / 删除 / 复制 / 导入 / 剪藏、
  模板与来源保存、工作区创建与切换……）；
- **新增守卫**（`src/lib/failureFeedback.test.ts`）：禁止别处再写
  `toast.error(errorMessage(…))` / `toast.error(Store.error)`——新写的失败路径若绕过统一入口，
  测试直接失败（反向验证过：故意改回一处立刻被抓）。

### 证据不足就说不足：查询扩展 + 证据充分性（Track D5 / N9）

研究助手原来的失败方式不是"答错"，而是**硬答**：材料只覆盖了 5 个子问题里的 1 个，
报告照样生成，读起来还挺完整——用户没有任何线索能看出来。这一版把这条路堵上：

- **查询扩展**（`src-tauri/src/application/ai/query_expansion.rs`）：一次检索只发课题原文太容易漏，
  现在把课题扩成**最多 6 条**查询——课题原文（永远第一条）→ 括号里的短语 → 按连接词
  （与/和/及/或/、/，//…）切开的片段 → 拉丁词（`Rust` / `SQLite` / `FTS5`）。
  **刻意不做**同义词替换、拼写纠错、凭空造词：那些要语义模型，规则瞎猜只会把噪声引进来源列表。
  规则化还有个好处：离线、零成本、每次结果一样，可复现；
- **收集按扩展查询逐条检索再按笔记去重合并**（课题原文的结果排在前面），
  计划里记录**本次实际用了哪几条查询**，界面与报告都能看到；
- **证据充分性**（`src-tauri/src/application/ai/evidence.rs`）：六个缺口逐条判定——
  一条材料都没有 / 有子问题完全没覆盖 / 没有 ≥2 个独立来源 / 可用来源太薄 / 只有 E 级线索 /
  可用来源全部可能已过时。**任一不满足就判"不足"**，并点名影响哪些子问题、涉及哪些来源；
- **不足时的行为是"明说不够"，三处同时说**：报告顶部「证据充分性：不足 + 缺口 + 怎么补」、
  警告块新增 `insufficientEvidence`、结论段显示
  "_证据不足，本次**不给结论**（不是「查过没有」）_"；界面上新增「证据充分性」面板（红/绿），
  不用去 markdown 里翻；
- **口径唯一**：判定用的"独立来源"与结论段的交叉验证**共用 `evidence::source_identity`**
  （同一站点多篇只算一个），不会出现"评估说够、结论段却一条都进不去"；
- 预览端（mock）与后端**同规则、同阈值**（同名常量），不会出现"预览里能出结论、真机上不出"。

**真机口径的验证**（`src-tauri/tests/evidence_sufficiency_flow.rs`，3 条）：

| 场景 | 期望 | 结果 |
| --- | --- | --- |
| 库里没有相关材料 | 判"不足"，不产出结论，报告明说 | ✅ 缺口为 `noMaterial`，结论段为空 |
| 5 个子问题各 2 篇独立来源 | 判"充分"，正常给结论 | ✅ 覆盖 5/5，结论非空（证明不是"永远说不足"） |
| 只命中扩展查询的笔记（课题原文查不到） | 也要被收进来 | ✅ 控制组先证明课题原文确实查不到它，扩展后它出现在来源里 |

两个模块另有 13 条单测（连接词切分、括号短语、拉丁词、去重、上限、同站点只算一个独立来源等）。

### 缺陷修复（P0）：切笔记时的「迟到的保存」会把正文写空（2026-10-11，真机验收发现）

**现场（用户复现）**：从「目录管理」进入笔记 A 正常；退回目录管理再进入笔记 B，编辑区在
A 与 B 之间**频闪**；继续换一篇，频闪对象变成「上一条笔记」。我在真机上抓到服务端日志：

```text
note_save id=…42NBAG title="调研报告：工作窃取调度策略" content_len=944   ← 正常（离开这篇时的落盘）
note_save id=…42NBAG title=""                        content_len=0     ← ！！空标题 + 空内容写进同一篇
note_save id=…cccc0003 title="验收笔记C"             content_len=142   ← 正常
```

即：**频闪与丢正文是同一个根因**——切笔记的中间帧里编辑器状态与 `detail` 错配，
而这个错配被写成了一次真实落盘。验收用的临时库里先后有 5 篇笔记的正文被写空
（都从 `.knowledge/history/` 的快照恢复，也再次证明版本历史是救命的那一层）。

**三处防线（都能证伪）**：

1. `notesStore.save()`：**保存「界面上已经不在这一篇」的笔记时，不再把 `detail` 换回去**。
   以前它无条件 `set({ detail })`：路由要打开 B、detail 被改回 A，`NotesSection` 的 effect
   见 `detail.note.id !== 路由 id` 又去打开 B —— 来回切换就是用户看到的频闪（+2 项测试）；
2. 编辑器新增 `editorContentBelongsTo(loadedId, detailId)` 守卫：**编辑器还没装载这篇的内容时拒绝落盘**
   （切笔记的中间帧正是这种状态，落盘就会把上一篇的内容写进新笔记）（+3 项测试）；
3. `useAutosave.flush()`：**没有改动就不发保存请求**。以前每次切笔记 / 离开编辑器都无条件写一次，
   正是它把中间帧放大成了数据风险；改用显式 `dirty` 标记，兼顾「切走前一定落盘」与
   「没改就不写」（+1 项测试，且没有破坏既有的 3 项）。

三处守卫都做过反向验证（临时破坏 → 5 项测试立即红 → 还原）。真机复验：同一路径连跑一遍，
连拍帧稳定、**四篇笔记文件字节数完全不变**（不再被写空）。

**根因坐实（同一晚，按计划追这条线）**：源头在 `NoteService::detail()`——

```rust
let stored = match self.ctx.storage.read_note(&note.file_path) {
    Ok(stored) => Some(stored),
    Err(_) => None,        // ← 读取失败被静默吞掉
};
let content = stored.map(|s| s.body).unwrap_or_default();   // ← 于是「正文 = 空字符串」
```

**读文件失败被降级成「这篇笔记的正文是空的」**，前端把空正文同步进编辑器，
下一次保存就把空内容写回文件——真机上 5 篇笔记被写空的**起点**就在这里。

修复：只有**扫描器已经标记 `missing`** 的笔记才按空正文返回（界面据此提示「笔记缺失」，
这也是既有约定）；**其它任何读取失败一律如实报错**，让界面显示「无法打开这篇笔记」，
而不是给一个看起来正常的空编辑器。

测试：`tests/external_interference_flow.rs` 新增 1 项——文件被移走且尚未扫描时 `get` 必须报错、
被标成 `missing` 后仍可读（空正文）。反向验证过：改回 `Err(_) => None` 该测试立即失败。

### 缺陷修复：PDF「打印视图」报 `open_path not allowed by ACL`（2026-10-11，真机验收发现）

**现场表现**：笔记 → 「导出…」→ 选 PDF（打印视图）→ 点「打开打印视图」，
弹出 `Command plugin:opener|open_path not allowed by ACL`，打印流程整条走不通；
同一处问题也让「设置 → 工作区目录 → 打开」失效（那里只是把错误吞成一句 toast）。

**根因**：前端调的是 `openPath`（`@tauri-apps/plugin-opener`），而能力声明里只有
`opener:default` —— 这个默认集**只含 `open_url` 与 `reveal_item_in_dir`，不含 `open_path`**。
只有真机点下去才会暴露：组件测试与浏览器 E2E 都碰不到 Tauri 的 ACL。

**修复**（`src-tauri/capabilities/default.json`）：显式放行 `opener:allow-open-path`，
并给出**非空 scope**（这类权限不带 scope 等于一条路径都不允许）：
家目录 / 临时目录 / 应用数据目录 / 外接卷 / `/tmp`。放行范围是「用户自己选定过的位置」
（工作区根目录、刚导出的文件），应用不会把笔记内容里的字符串当路径传进来。

**守卫**（`src/lib/pluginPermissions.test.ts`，2 项）：扫描前端对 `plugin-opener` 的 import，
逐个比对权限标识；并检查 `open_path` 的 scope 非空。去掉权限立刻红（已反向验证）。
这类「前端调用 ↔ ACL 不匹配」以后在 `pnpm test` 就会失败，而不是等到真机上弹 ACL 错误。

### 缺陷修复：切换知识库后列表不更新（2026-10-11，真机验收发现）

**现场表现**：从「验收临时库」切到 `knowledge` 后，侧边栏计数已经是新库的
（全部笔记 3），但中栏一直显示「这里还没有笔记」、状态栏还挂着
「笔记不存在或已被删除。」——得先在新库上做点别的操作（换筛选 / 换路由）才会顺带刷新。

**根因**：切库只调了 `notesStore.reset()`（清空 items / detail），**没有任何人再去取一次列表**；
刷新完全依赖页面组件里「路由 / 筛选变化」的 effect，而切库不改路由 → 永远不刷新。
更糟的是 URL 还停在 `/notes/<旧库笔记 id>`，`NotesSection` 的 effect 紧接着去
`openDetail(旧 id)` → `NOTE_NOT_FOUND` → 那句「笔记不存在或已被删除。」。

**修复**（两处，互为兜底）：

- `notesStore.reloadForWorkspace()`：清掉上一个库的视图状态（列表 / 详情 / 选中 / 关键词 /
  多选 /「不在目录中」）**并立刻按新库重新取列表**；`WorkspaceSwitcher` 的「切换知识库」
  与「打开知识库」改用它，并且在离开当前笔记路由时回到列表（`/notes`），不再对一个
  不属于新库的 id 发请求；
- `useWorkspaceEvents` 增加按 `workspaceId` 的兜底刷新（列表 / 统计 / 分类 / 标签）——
  以后任何「换工作区」的新入口都不会再漏掉这一步。

**证据**：新增 `src/stores/notesStore.workspaceSwitch.test.ts`（2 项，先写失败复现）；
真机复测（本机 1.2.1，2026-10-11）：切到 `knowledge` 后首页显示新库自身统计、
底栏「当前列表 3 条」、无过期错误提示。

### 在线模型（OpenAI 兼容）：给「跑不动本地模型」的机器留的一档（2026-10-11）

前提是用户提的那句实话：**应用是本地软件、跨平台部署，但不是每台机器都跑得动本地模型**
（没有独显、内存不够、公司机器不允许装 Ollama）。于是一代的模型档位做成三层降级链：
**模板实现（永远可用）→ 本地模型 → 在线模型**，调用点只有两处
（`decision_candidates()` 打分 / `composer_candidates()` 写报告），任何一档失败自动降级，
研究流程不会因为模型不可用而卡住。

- **在线 provider**（`application/ai/remote_model.rs`）：OpenAI 兼容端点 `POST {base}/chat/completions`，
  生成与打分共用一份提示词（与本地模型**同一份**，避免「换模型后报告口径变了」）；
  失败信息只带主机名与状态码，**绝不回显 API Key**；

  未授权时**根本不构造 provider**，所以「未授权 = 一个字节都不外发」是结构保证；
  拒绝同样记 `outbound=false` 审计（`REMOTE_MODEL_UNCONFIGURED` / `REMOTE_MODEL_UNCONFIRMED`）；
- **换收件人即作废**：基地址或模型名变更会清空 `remoteModelAuthorizedAt`，需要重新确认一次
  （与「切联网档位清确认」同一规则）；
- **地址两层校验**：写入侧 `normalize_remote_base_url` 只放行 `https://` 公网域名
  （本机可写 `localhost`），拒绝裸 IP、十进制/十六进制写法（`2130706433`）、单标签主机名、
  带 userinfo 的地址；读取侧在构造 provider 之前再校验一次，直接改库也发不出去；
- **API Key 只写不读**：新增 `infrastructure/credential_store.rs`，Key 存应用数据目录的
  `ai-credentials.json`（Unix `0600`）——**不进工作区**（否则会被备份包与导出的 Markdown 带走），
  IPC 响应 / 审计 / 日志里只回显 `remoteModelKeySet` 布尔值，输入框保存后立即清空；
  清除 Key 会连文件一起删掉；
- **报告如实标注**：用在线模型生成的报告与附录写明「在线模型 + 材料片段已离开本机、
  可能被服务商留存」，不再与本地模型共用同一句「模型生成」；
  报告的 Markdown 头与界面也不再对模型写的报告标注「未接入模型」；
- **设置页**新增「在线模型（OpenAI 兼容端点）」区块：地址 / 模型名 / API Key（保存、清除、
  已配置徽标）/ 两个开关 / 授权状态行 / 首次授权说明对话框；

- 测试：`src-tauri/tests/remote_model_flow.rs` 7 个集成测试（授权后真的调用且请求头带 Key、

### 缺陷修复：动作失败却提示「成功」（2026-10-11）

**症状**：一批写操作在失败时会**弹出成功提示**。例如「移到回收站」失败仍提示「已移入回收站」、
「永久删除」失败仍提示「已永久删除」、「重建索引」失败仍提示「索引已重建」、
批量删除的「撤销」里有一半恢复失败仍提示「已恢复 2 篇笔记」。用户会以为数据已经按他点的做了。

**根因**：各 zustand store 的写操作把错误收敛进自己的 `error` 状态而不是抛出（这样界面不会崩），
但调用处普遍写成 `void action(id).then(() => toast.success(...))`——`.then` 在失败时照样执行。

**修复**（约定化，避免复发）：

1. store 的写操作改为返回 `boolean`（`notesStore` 的 remove/restore/purge/duplicate/toggleFavorite/setPinned、
   `tagsStore.remove`、`workspaceStore.rebuildIndex`、`searchStore.rebuildIndex`）；
2. 新增 `src/lib/actionFeedback.ts` 的 `reportAction(ok, success, errorMessage, fallbackError)`：
   成功报成功、失败报错并带上 store 里的原因；
3. 逐个修正调用点：笔记条目菜单（收藏/置顶/恢复/删除/副本/永久删除）、编辑器菜单（同样六处）、
   删除确认对话框（含「含子文档」的撤销计数）、标签删除、三处「重建索引」；
4. **批量撤销如实计数**：`已恢复 1/2 篇，1 篇失败：笔记不存在。`——不再把一半失败报成全部成功。

**测试**：`src/lib/actionFeedback.test.ts` 3 项（成功/失败带原因/无原因兜底）；
`notesStore.filters.test.ts` 增 2 项（撤销部分失败 → 报错且含数量与原因、不报成功；单篇恢复失败返回 false）。

同时修掉两处「失败看起来像别的状态」的加载路径：

- **设置 → AI**：读取策略失败时原来会一直显示「正在读取 AI 策略…」（像卡住），现在明确报错并给「重试」；
- **快速切换（⌘/Ctrl + P）**：读取笔记失败时原来显示「没有匹配的标题」（像没搜到），
  现在显示「读取笔记失败 + 原因 + 重试」，重试成功后恢复正常列表。

测试：`AiSettingsPanel.test.tsx` / `QuickSwitcherDialog.test.tsx` 各增 1 项。

### 缺陷修复：重命名父文档没有同步子文档的 `parent:` 声明（2026-10-11）

**测试**（`tests/rebuild_flow.rs` 第 4 项）：父文档 + 按标题声明的子文档 → 改名后子文档的

### 新增守卫：命令契约（前端 ↔ 注册表 ↔ mock）（2026-10-11）

前端是用字符串调 Tauri 命令的（`call('note_create', …)`），编译器管不到、E2E 又只跑 mock，

新增 `src-tauri/tests/command_contract.rs` 把三份清单对齐并作为常规测试跑：

- 前端 `services/*.ts` 调用的每个命令都必须在 `lib.rs` 注册（否则桌面端直接失败）；
- 也必须在 mock 里有 `case` 分支（否则浏览器预览失败）；
- `lib.rs` 注册的每个函数都要能在 `commands/` 里找到定义；

### 缺陷修复：外部新增 / 删库重建后子文档层级丢失（2026-10-11）

**症状**：`.knowledge/database.sqlite` 被删除后重新打开工作区（或以文件监听方式外部新增一篇
`parent:` 指向某篇文档的 Markdown），子文档在列表里**显示成顶层**——文件里的 `parent:` 明明写着。

**根因**：扫描有两条采纳路径。批量路径（一次新增 > 50 篇）在批次结束后统一解析 `parent`；
**单文件路径**（监听回调、零散新增、小库重扫——也就是常见情形）采纳时直接按文件顺序写库，
既没有解析 `parent`，而且即便当场解析也可能「子文档先于父文档被读到」。

**修复**（`application/index_service.rs`）：

1. 从批量路径里抽出 `resolve_declared_parents()`（id 优先、其次按标题匹配，且防自指）；
2. 单文件路径采纳时把「声明了父文档」的笔记收集起来，**等整轮扫描结束再统一解析**；
   批量路径复用同一个函数，两条路径行为一致。

**测试**：新增 `src-tauri/tests/rebuild_flow.rs` 2 项——
① 删库重建：id 稳定、分类/标签/置顶/手动顺序/父子层级/来源与时效/双向链接/FTS 全部从 Markdown 复原；
② 外部新增一篇按**标题**声明父文档的子文档，一次扫描后层级即生效（不再需要等下一次外部编辑）。

**已知残留**（记录在验收清单的「已知限制」）：若子文档先被采纳、父文档在**更晚的另一轮扫描**里才出现，
子文档的层级要等它下次被外部编辑时才补上；手动拖进父文档或编辑一次即可。

### 不变量补测：AI 不写库 / 文件即事实来源 / 检索源受域名规则约束（2026-10-11）

按「0 信任」把文档里承诺过、但之前没有测试证据的三条不变量补上：

1. **写入提案之前，AI 不碰工作区**（`research_steps_before_write_touch_nothing_on_disk`）：
   走完立项 → 收集 → 验证 → 汇总 → 提案之后，笔记数与 Markdown 文件清单**完全不变**，
   且研究会话（`.knowledge/research/*.json`）不会混进可扫描的 Markdown；
2. **文件是唯一事实来源 + 落库即可检索**（`written_report_is_a_normal_markdown_note_and_becomes_searchable`）：
   直接读磁盘上的那份 Markdown，断言 frontmatter 里 `id` / `source_type: research` /
   `source_reliability` / `valid_until` / `source_ref` / 标签都对得上，正文含报告抬头；
   随后**立刻**用 FTS 检索到这篇笔记（索引在写入时已更新，不需要等下次扫描）；
3. **每一步都被闸门挡住 + 拒绝也要留痕**（`every_research_step_is_gated_by_the_ai_switch`）：
   关掉总开关后 collect / verify / compose / proposal / write / abort 全部返回 `AI_DISABLED`，
   审计里至少 6 条 `denied` 记录且 `outbound` 全为 false；而**读取会话**不受影响（草稿不丢）；
4. **检索源本身也受域名白名单约束**（`search_endpoint_itself_is_subject_to_the_domain_allowlist`）：
   白名单非空且不含检索源主机时返回 `NETWORK_DISABLED` 且**一次请求都不发**；

### 不变量补测：回收站恢复不覆盖他人文件（2026-10-11）

### 缺陷修复：被标记「缺失」的笔记无法恢复（2026-10-11）

**症状**：把一篇笔记的文件移出工作区（或在外部删掉）后，扫描会把它标记为**缺失**；
但把文件**放回去**再扫描，笔记**永远不会恢复**——仍然停在「缺失」，也搜不到。
用户最直觉的补救动作（把文件放回原处）完全无效，只能重建知识库或删库重建。

**根因**：`apply_external_edit` 里其实写了「缺失 → 正常」的恢复分支，但**永远走不到**：
扫描的候选集合 `by_path` 只装 `Active` 状态的笔记，缺失笔记不在其中；文件放回后被当成
「新文件」，而 `adopt_file`/`adopt_files_batched` 又会因为「路径已存在」跳过它。
（整目录被移走再放回的情况同样如此。）

**修复**（`application/index_service.rs`）：

1. 扫描候选集合改为 **Active + Missing**；
2. 候选里 status 为 `Missing` 且文件已回到磁盘的，直接走 `apply_external_edit`——
   它会把状态翻回正常、同步元数据、**重建索引 / 链接 / 关系**，并计入 `updated`；
3. 仍不在磁盘上的缺失笔记在收尾循环里跳过，避免每轮扫描重复计数与重复发事件。

**测试**：新增 `tests/external_interference_flow.rs` 3 项——① 整目录被外部删除：
扫描如实报缺失或报错、保存返回明确错误、**不 panic**；② 整目录被移走再放回：
无需重启即可恢复，笔记仍在库里；③ **单文件移出再放回**：先标记缺失 → 文件回来后
恢复为正常笔记、正文读得回来、并**重新进入检索索引**。

### 缺陷修复：防抖窗口内切换笔记会丢改动（2026-10-11）

**症状**：自动保存有防抖窗口（默认 1000ms）。输入后立刻点到另一篇笔记（或离开编辑器）时，
待保存的改动**不会被写盘**——回到原笔记，刚才敲的那几行不见了。属于静默丢数据。

**修复**：

- `useAutosave` 新增 `flush()`：取消防抖等待、立即落盘（无改动时调用也安全，
  `onSave` 自身会判断是否需要写）；
- `notesStore.openDetail(id, options?)` 在**切换笔记前**先调用编辑器注册的 flush
  （`registerEditorFlush`，编辑器挂载时注册、卸载时注销并再保险 flush 一次）；
  传入 `{ discardLocalEdits: true }` 可显式跳过——冲突对话框的「重新加载磁盘内容」正是
  用户主动放弃本地编辑的场景，**不能**把本地内容写回去。

**测试**：

- `src/hooks/useAutosave.test.ts` 3 项（防抖/去重、`flush` 立即落盘且不会补一次、关闭自动保存时仍可手动 flush）；
- `src/stores/raceGuard.test.ts` 增 1 项：切换前**顺序**必须是「先 flush 再取新详情」、
  同一篇刷新不触发、`discardLocalEdits` 时跳过；
- E2E 第 5c 步（真实操作）：把自动保存延迟设为 3000ms → 输入一行 → **立刻**切到另一篇
  （此刻防抖还没到）→ 切回来，断言那行字还在。

### 缺陷修复：快速切换时的异步竞态（2026-10-11）

**症状**：连着快速点几篇笔记时，先发出的详情请求可能**后返回**——旧响应会覆盖新状态，

**根因**：`notesStore.openDetail` / `refresh` 与 `searchStore.run` 拿到响应就无条件写 store，

**测试**：`src/stores/raceGuard.test.ts` 3 项（守卫本身的语义；**慢的 A 后到不能覆盖快的 B**；
旧关键词结果不能覆盖新关键词结果）。反向验证过：临时撤掉 `openDetail` 的守卫，

- **失败即降级**：没装 Ollama / 没 pull / 超时 / 输出不合规时——打分退回规则档、报告退回模板实现，

### 目录分组：语义结论（阶段 C5，2026-10-11）

语雀的「分组」是目录里的**非文档容器**（能装文档、自己不是文档）。经核对当前实现，结论是
**不新增节点类型**——已有能力已覆盖组织需求，只补了可发现性：

| 语雀分组的能力 | 本应用的对应实现 | 证据 |
| --- | --- | --- |
| 目录里嵌套的容器，可折叠 | **子文档层级**（父文档 + 子文档，任意层深） | `lib/noteTree.ts` 递归建树；列表行带折叠箭头 |
| 把文档归到一个分组下 | 拖到条目中间即成为其子文档；条目菜单「创建子文档」 | V1.2.1 拖拽语义与 `note_set_parent` |
| 分组本身不承载内容 | 父文档**正文可以留空**（没有任何必填正文的约束） | `note_create` 只要求标题 |
| 分组的分类归属 | 子文档默认**继承父文档分类** | `NoteService::create` / CreateChildNoteDialog |

差异（如实记录）：语雀的分组不是文档、点不开；我们的「分组」本身是一篇（可为空的）文档，
因此它能被打开、被链接、被搜索——这是本地 Markdown 模型下的取舍，不额外造一种节点类型。
可发现性补强：新建子文档对话框的说明里明确写出「父文档也可以只当分组用（正文留空、标题写分组名）」。

### 稳定性：扫描与文件监听并发（阶段 B，2026-10-10）

- 新增并发测试 `src-tauri/tests/concurrency_scan_flow.rs`（3 项，屏障对齐同刻起跑）：

### 缺陷修复：父文档晚于子文档出现时，层级要等下次编辑才补上（2026-10-11）

**症状**：把一篇**子文档**先放进工作区（它的 frontmatter 写着 `parent: 父文档`，而父文档此刻
还不存在），扫描按顶层展示——这条没错。但之后父文档拷进来、扫描也采纳了它，
**子文档仍停在顶层**：要等这篇子文档下次被外部编辑（或手动拖一次）才会归位。

**根因**：扫描末尾的 `resolve_declared_parents` 只在「本轮采纳的文件」里找声明，
而子文档是**前几轮**采纳的；`parent_id` 解析失败后线索就丢了——库里只存解析结果，
没存声明原文，因此后续轮次无从知道「还有谁在等父文档」。

**修复**：

1. **迁移 010**：`notes` 新增派生列 `declared_parent`（+ `idx_notes_declared_parent`），
   保存 `parent:` 的**原文**（id 或标题）。它和 `parent_id` / `sort_order` / `pinned` 一样
   由 frontmatter 投影而来，删库重扫即可重建；`SCHEMA_VERSION` 升到 **10**；
2. **解析失败也留线索**：`resolve_declared_parents` 在解析不到父文档时写入声明原文
   （而不是像以前那样什么也不做）；重命名父文档时，子文档的声明原文与文件一起改写；
3. **每轮重试**：整库扫描与文件监听两条入口在「本轮有新增 / 更新」时，
   对「声明了父文档但还没解析成功」的子文档补一次解析——只需一次带索引的小查询，
   不必为找它们去读全库文件（大库扫描的 mtime 短路优化不受影响）。

**测试**：`tests/external_interference_flow.rs` 新增 2 项——子文档先到、父文档后到，
**整库扫描**与**文件监听**两条入口都在同一轮内把层级补上，且声明原文留在库里。
反向验证过：临时让重试直接返回 0，两条用例立刻失败（`left: None, right: Some(...)`）。
Rust 全量 36 个测试目标全绿。

**基准复测**（迁移改动动了扫描写库路径）：1 万篇扫描采纳 3.76 s、检索平均 18.6 ms /
p95 44.4 ms、召回 100%；3 万篇图谱 `graph_get` 全量 **843.7 ms**（红线 1.5 s）——
均无退化。

### 缺陷修复：E 级（不可用）来源被算成交叉验证，连引用一起进了结论段（2026-10-11）

**症状**：规格 §9.3 写明 E 级来源（论坛贴 / 社交平台 / AI 生成 / 无法判定出处）**只作线索、
不进结论段**，警告块也这么写。但实测：同一子问题下「一条 A 级官方文档 + 一条 E 级社交平台帖子」，
两条被当成「两个独立来源」→ `cross_verified = true` → 该条结论**同时进入「结论先行」与
「关键事实」段**，并且把 E 级那条作为引用 `[2]` 挂在结论后面。也就是警告说一套、报告写另一套，
而且「权威性可验证」这个产品承诺被绕过了。

**修复**（`application/ai/research.rs` 的验证阶段）：

1. **E 级不参与任何判定**：不计入独立来源数（不参与交叉验证）、不参与冲突判定、
   不进引用列表（`citations`）；可用来源不足 2 条时该子问题只能进「待验证清单」；
2. **只有 E 级来源时不静默**：仍生成一条线索（引用这些 E 级来源），正文写
   「只有不可用来源（E 级）作线索，未形成可引用结论」，第 5 段的原因也如实写成
   「只有不可用来源（E 级）作线索，建议补充可信来源」（此前会含糊地写成「只有单一来源」）；
3. 浏览器预览端（mock）同规则，避免两端分叉。

**测试**：`tests/web_search_flow.rs` 新增 1 项——用本机一次性 HTTP 服务返回
「A 级官方文档 + E 级社交平台帖子 + E 级风险吐槽」三条候选，断言

### 缺陷修复：只在 `<meta charset>` 里声明 GBK 的中文网页完全抓不下来（2026-10-11）

**症状**：剪藏一个「HTTP 头不带 charset、只在 `<meta charset="gbk">` 里声明编码」的页面

「读取网页失败：io: stream did not contain valid UTF-8（超过 3 MB 的页面请改用其它方式保存）」
——原因和大小毫无关系，用户按提示去换工具是白费功夫。

**根因**：正文直接用 `read_to_string()` 按 UTF-8 读；`ureq` 的 charset 特性**只在
Content-Type 声明了非 UTF-8 编码时**才转码，没声明时是 PassThrough，GBK 字节直接被判为非法 UTF-8。

**修复**（`application/clip_service.rs`）：

1. 改成读**原始字节**再自己解码，并按「ureq 是否已经解过」分两种情况（这一点读 ureq 源码确认过，
   否则会对已解好的文本再解一次、反而变乱码——这个回归在实现过程中真的出现过一次，被测试抓住）；
2. 无声明时的兜底顺序：BOM → HTML `<meta charset>` → **严格 UTF-8** → **GBK**；
   GBK 解码复用已在依赖树里的 `encoding_rs`（ureq 的 charset 特性带入，**不新增第三方依赖**，
   Cargo.toml 只多了显式声明）；
3. 错误信息不再误导：区分「超过 3 MB」与「读取失败（网络/不可公开访问）」，
   空响应单独报「页面返回了空内容」。

**测试**：`tests/clip_flow.rs` 从 2 项扩到 5 项——GBK 声明在 Content-Type（保持可用）、
**声明只在 meta**（本次修的主场景）、**完全没有声明**（UTF-8 严格失败后按 GBK 兜底）；
测试服务端改为按**字节**写响应（Content-Length 用字节长度），否则非 UTF-8 页面根本造不出来。
反向验证过（把解码退化成 `from_utf8_lossy` → 两条新用例立即失败）。

### 缺陷修复：备份漏了版本历史 / 模板 / 回收站；恢复出来的库还会「换身份」（2026-10-11）

**症状**（两个连在一起的问题，都是静默丢数据）：

1. **备份包内容不全**：`backup_create` 只收集「活跃笔记 + 附件 + 数据库 + 配置」，
   版本历史（含命名版本）、模板、回收站都没进包——文档写的却是「包含全部 Markdown、附件、

   快照里的行全成孤儿：**回收站列表、收藏这类「只存在数据库里」的状态看不见了**
   （回收站的文件虽然还在 `.trash/`，但没有任何一行指向它）。
   同样的坑也出现在文档推荐的搬迁方式「把整个知识库目录复制过去，在新机器上打开」上。

**修复**：

1. `backup_create` 追加 `.knowledge/history`、`.knowledge/templates`、`.trash` 三类文件
   （`collect_relative_files` 递归收集）；备份内容的边界写进文档
   （不入包：`.knowledge/research` 可丢弃的中间产物、`.knowledge/logs` AI 审计元数据、备份目录自身）；
2. 备份清单与校验改为**四类分别计数**（笔记 / 附件 / 历史·模板 Markdown / 回收站 Markdown），
   写入与校验共用同一套 `classify_entry`，避免「清单说 N 个、实际 M 个」自相矛盾；
   新增的两个计数带 `serde(default)`，旧备份包仍可解析校验；
3. `WorkspaceService::open` 在「按路径查不到、但库里已有记录」时**沿用原身份**：
   保留 id、把 `root_path` 指到新位置。应用级「最近打开」按 id upsert，
   因此同一份备份恢复到多处时列表里只保留最近打开的那个路径。

**测试**：`tests/rebuild_flow.rs` 增 1 项——建活笔记（存命名版本 + 收藏）+ 附件 + 模板 +
回收站，然后备份 → 校验 → 恢复到空目录 → 打开，断言：**恢复后 workspace id 与原来一致**、

### 加固：本地模型地址「读取侧再校验一次」（纵深防御）（2026-10-11）

**修复**：`AiPolicyService::local_model()` 在读取时用 `normalize_local_endpoint` 再校验一次，

### 缺陷修复：本地模型地址校验（唯一的外发闸门）漏了测试，且 `::1` 分支是死代码（2026-10-11）

**症状**：AI_ARCHITECTURE_PLAN §9.7 写「本地模型只连本机（`localhost` / `127.0.0.1` / `::1`）」，
实测两点都不成立：

1. `normalize_local_endpoint` **一个单元测试都没有**——这条规则是「外发通道」的唯一防线，
   却只靠代码读起来对；
2. **`::1` 分支永远不会命中**：主机名解析用 `split(':').next()` 取端口前的主机，
   `[::1]:11434` 会被切成 `[`，裸 `::1` 会被切成空串——文档写了支持 IPv6 本机地址，实际用不了。

顺带发现同一个「取主机名」逻辑在 `policy.rs` 与 `source_grade.rs` **各写了一份**（逐行几乎相同）：
两处口径一旦漂移，「黑名单到底拦住谁」「来源怎么分级」就会变成说不清的事。

**修复**：

1. 抽出 `application/ai/host.rs` 的 `host_of()` 作为**唯一实现**（小写 → 去 `www.` / 端口 / userinfo；
   IPv6 字面量去方括号），闸门、白黑名单、来源分级、本地模型地址校验全部复用；
   顺手修掉「先去 `www.` 再小写」的顺序错误（大写 `WWW.Example.com` 去不掉前缀）；
2. 本地模型地址：`localhost` / `127.0.0.1` / `[::1]` 均可用（IPv6 地址按用户原样保存，
   拼 `…/api/generate` 时方括号仍保留，URL 合法）；
3. **补测试**（此前为零）：接受的写法（含端口 / 路径 / 大写 / IPv6）与
   **拒绝的绕过写法**（`localhost.evil.com`、`127.0.0.1.evil.com`、`evil.com#@localhost`、
   `user@evil.com`、十进制 IP `2130706433`、`0.0.0.0`、非 http(s)、缺 scheme）各一组；
   另加 IPv6 在「域名规则」与「主机解析」两侧口径一致的断言。

**反向验证**：去掉 `::1` → 接受的用例立即失败；把校验改成恒真 → 拒绝的用例立即失败。
Rust 38 个测试目标（库单测 116 项）全绿。

### 缺陷修复：运行中点「中止」会被正在跑的那一步覆盖回去（2026-10-11）

**症状**：规格 §9.2 / §9.7 承诺「用户可随时中止」，界面上的「中止并保留草稿」按钮
在忙碌时也是可点的。但中止与正在运行的步骤是**并发**的：中止把落库状态改成 `aborted`，
运行中的步骤随后用自己那份内存快照 `save`，又把状态写回 `collected` —— 用户点了中止，
看到的却是会话回到「已收集」，联网抓取也照旧跑完预算（实测：慢速检索源下必现）。

**修复**（`application/ai/research.rs`）：

1. 长步骤在每个关键节点以**磁盘上的状态**为准（`aborted_snapshot`）：
   收集在「本地部分跑完、联网之前」「每个候选之前」「收尾保存之前」都检查一次；
2. 一旦发现中止，**中止优先**：保持 `aborted` 状态与中止原因，并把这一步**已经拿到的成果**
   并回去（收集到的来源、验证结论、报告、提案都留作草稿），不白跑也不覆盖；
   步骤日志写明「…途中被用户中止：已得材料 N 条保留为草稿」；
3. 验证 / 汇总 / 提案三步同样加了收尾检查（同一个窗口，同一个口径）。

**测试**：新增 `tests/research_abort_flow.rs` 2 项——
① 联网收集途中中止（用一个 400ms 才回应的本机检索源，确保中止落在步骤运行中）：
   状态必须停在 `aborted`、中止原因保留、日志走「收集中途被用户中止」分支、
   且不再写「收集完成」记录；② 已中止的会话不能再推进（状态机挡住，返回 `INVALID_INPUT`）。
反向验证过（把 `aborted_snapshot` 改成恒返回 `None` → 用例立即失败）。
`ResearchPage.test.tsx` 增 1 项：步骤进行中「中止」按钮必须**可点**并真的调用后端

### 新增：研究助手实时进度事件（§9.2 的「每一步都发进度」）（2026-10-11）

### 缺陷修复：域名黑名单对「检索结果」其实没生效（2026-10-11）

**症状**：规格 §9.3 写「白名单可配置、**黑名单强制**（黑名单命中的来源直接丢弃，并计入报告附录）」。
但实现只在**抓正文**时校验域名（`web_fetch` 会拒绝黑名单域名），而「抓取正文」默认关闭
（只用检索摘要）——于是黑名单域名的搜索结果照样以「标题 + 摘要」的形式进入来源列表、
进入报告，用户以为已经屏蔽了某个站点，其实没有。白名单同理：不在白名单里的结果也会漏进来。

**修复**：

1. **候选逐条过域名策略**：`AiPolicyService::host_verdict()` 复用闸门二同一套匹配规则
   （子域匹配、`www.` 归一），检索结果里命中黑名单 / 不在白名单的候选**直接丢弃**，
   不进入来源列表，也就不可能进入结论段；
2. **丢弃要如实记账，不能悄悄少东西**：被丢弃的候选记进会话（`droppedSources`：
   URL / 域名 / 原因），并在报告的醒目警告块里点名——
   「有 N 条检索结果被域名策略丢弃（黑名单 X 条 / 不在白名单 Y 条）：…」；
   采集步骤日志也写明丢弃数量；
3. 类型与预览端同步：`ResearchWarningKind` 增 `droppedSources`、`ResearchSession` 增
   `droppedSources`（浏览器预览模式不联网，因此不会产生这类记录）。

**测试**：`tests/web_search_flow.rs` 新增 2 项——
① 黑名单命中：结果不进来源列表、`droppedSources` 记 1 条 `denylist`、报告警告块点名域名、
   参考来源段里没有它；② 白名单之外：同样丢弃并记为 `notAllowed`。
两项都反向验证过（把逐条裁决去掉 → 立即失败）。

实测（修复前，macOS aarch64 本机）：

| 项目 | 结果 |
| --- | --- |
| 写入 3000 个 Markdown 文件 | 159 ms |

基准暴露并已修复的两处缺陷：

1. **图谱节点被静默截断到 500**：`GraphService` 复用了 `NoteListQuery`，而列表查询单页上限 500，
   导致 3000 篇的库里图谱只返回 500 个节点（`truncated` 还是 false）。
   已改为按页取全量候选，再按 2000/5000 的图谱上限截断并正确置位 `truncated`；
2. **`links_rebuild` 退化为 O(N²)**：每篇笔记都重建一次标题索引（全表查询 + 建哈希表）
   并单独开事务，3000 篇下 51.7 s。已改为索引只构建一次、正文先读完、全部链接在**单个事务**内批量写入。

3. **扫描与文件监听并发不安全（已定位，修复待重做）**：文件监听回调走的是
   `IndexService::apply_file_changes`，它绕过 `scan_scope` 的「检查存在性 → 插入」序列；
   与显式 `scan_workspace()` 并发时，同一路径会被双方重复采纳，触发
   `UNIQUE constraint failed: notes.workspace_id, notes.file_path`，两侧扫描反复中止
   （复现：3000 篇时 active 卡在 375 —— 恰好一个分类目录的量）。

   `NoteService::create` 共用）在基准下验证有效，但会让 `file_watcher_reports_external_changes`
   集成测试挂起（监听线程持锁后与主线程形成锁序倒置），因此**已回退**。
   下一版方向：扫描改为单飞队列（watcher 只投递事件、由同一工作线程串行消费），
   或让采纳路径对插入冲突幂等（冲突时按外部修改同步，而不是报错中止整轮扫描）。

下表「修复后」列是在**临时互斥锁生效的构建**上测得的（`links_rebuild` 与 `graph_get`

基准的扫描步骤是时序相关的，可能再次触发上面的冲突 —— 待并发修复落地后统一复验。

| --- | --- | --- |

### 首次导入 1 万篇：6.3 分钟 → 4 秒（完成）

**目标**：把「首次导入 1 万篇」从约 6.5 分钟压到 1 分钟以内。**结果：4.0 s（带文件监听 4.2 s）**，提速约 90×。

三个真实原因（前两个都是「按 UNINDEXED / 未复用索引做逐篇操作」导致的 O(N²)）：

| 编号 | 原因 | 修法 |
| --- | --- | --- |
| R1 | FTS5 的 `note_id` 是 **UNINDEXED** 列，`DELETE … WHERE note_id = ?` 每篇都要全表扫描索引 | 新增 `search_documents_map(note_id → row_id)`（迁移 006），删除改按 **rowid 主键**；rowid 由 FTS5 `last_insert_rowid()` 分配（**不能用 `MAX(row_id)+1`，那同样是全表扫描**） |
| R2 | `RelationService::rebuild` 每篇都重建一次标题索引（O(N²)） | 标题索引整轮只构建一次，批量复用 |
| R3 | 单篇采纳要 4–6 次独立事务提交（记录/标签/FTS/标记已索引/快照） | 采纳改为**按批事务**：读取解析在事务外完成，200 篇一个事务批量写入（记录 + 标签 + FTS + 标记已索引） |

实测（`BENCH_NOTES=10000`，同一台机器）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 扫描采纳（停掉监听，单趟） | 388.9 s | **3.96 s** |
| 扫描采纳（带文件监听） | 486–493 s | **4.16 s** |
| FTS 全量重建 | 23.5 s | **4.2 s** |
| 提取阶段 / 写入阶段 | — | 0.47 s / 0.47 s（1 万篇） |
| 检索延迟（含摘要高亮） | 平均 18.1 ms / p95 44.2 ms | 平均 18.2 ms / p95 44.2 ms |
| 独特术语 / 混合写法 / 中文短语 recall | 100% / 100% / 100% | 100% / 100% / 100% |

**升级影响**：迁移 006 会创建映射表并清空既有 FTS 索引（旧索引没有 rowid 映射）；
应用下次打开工作区时会检测「已索引 < 总数」并**自动重建一次**（实测 1 万篇约 4 秒）。

### 基准发现的两个问题：修复其一、其二定位到更深一层（V1.1.2 开发中）

**① 混合中英文写法召回 0% —— 已修复。**
根因：查询表达式把 `术语A7F3` 拆成「CJK 双字」AND「拉丁前缀」两个条件，
而索引侧（unicode61）把它当作**一个整 token**，两个条件必然同时落空。
修复：`build_fts_match` 先按空白切块，**混合块整体作为前缀短语**（`"术语a7f3"*`）；
纯中文仍是双字短语、纯英文仍是前缀，语义不变。新增单测覆盖四种写法。

实测（`BENCH_NOTES=10000`）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 混合写法 `术语XXXX` recall@5 | **0%** | **100%** |
| 纯英文 `termXXXX` recall@5 | 100% | 100% |
| 中文四字短语命中率 | 100% | 100% |
| 检索延迟（含摘要高亮） | 平均 18.1 ms / p95 44.2 ms | 平均 17.9 ms / p95 43.5 ms |

**② 首次采纳大目录耗时超线性 —— 已定位到采纳路径内部（下一轮批事务化）。**

已做的改动（保留）：采纳路径不再**逐篇**刷新链接与关系（每篇都会重建一次标题索引 → O(N²)），
改为「本轮真正要采纳的数量 > 50 时，整轮结束后统一重建一次」，监听批次同理。

但 1 万篇实测**没有改善**（306 s → 392 s → 400 s → 486 s，含机器负载波动），
说明主因不在链接索引重建，而在更深的两层：

1. **每篇笔记 4–6 次独立提交**（插入记录 / 建标签 / 写 FTS / 标记已索引各自一个事务），
   1 万篇 ≈ 5 万次事务提交；
2. **轮询式文件监听每 3 秒做一次全库扫描**：`scan_scope` 对每个文件都要读取 + 计算 sha256
   才能判断是否变化（1 万次读取 + 哈希），导入期间与采纳重叠，成倍放大耗时。

**已实施「mtime + size 短路」**（迁移 005：`notes.file_size` / `notes.file_mtime`）：
扫描与监听先比对快照，未变化的文件不再读取全文与计算 sha256；应用自身写入后会刷新快照。
这对**稳态扫描**（打开工作区、轮询监听）有效，但对「首次采纳新文件」无效——
因为新文件本来就没有快照可短路。

**对照实验（关键证据）**：用 `BENCH_STOP_WATCHER=1` 停掉文件监听，单独测采纳本身：

| 规模 | 停掉监听 | 单篇耗时 |
| --- | --- | --- |
| 2000 篇 | **14.2 s** | 7.1 ms |
| 10000 篇 | **388.9 s** | **38.9 ms** |

两者都是「单趟扫描」，说明**超线性发生在采纳路径内部**（不是监听叠加）。
按每篇分解：读取+解析+sha256 ≈ 1 ms、FTS 插入 ≈ 2.3 ms（1 万篇实测 FTS 全量重建 22.8 s）、
而 4–6 次独立事务提交（记录 / 标签 / FTS / 标记已索引 / 快照）在库增长后成为主要开销
（WAL 检查点随库体积变贵）。

**下一步（唯一正确的修法）**：采纳按批事务化——每 200 篇一个事务，
把「每篇 4–6 次提交」降到「每批 1 次」，同时显著减少 WAL 检查点次数。
需要把 `&Connection`/`&Transaction` 参数贯穿 `adopt_file` → `TagService` / `IndexService`，
避免在 `with_conn` 回调内再次 `with_conn`（现有实现的已知死锁点）。

| 检索延迟（含摘要高亮） | 平均 0.7 ms / p95 1.7 ms | **平均 18.1 ms / p95 44.2 ms** |
| 中文四字短语命中率（“查询优化”） | 100% | **100%** |
| 纯英文 token recall@5 | 100% | **100%** |
| 混合写法「术语A7F3」recall@5 | 0% | **0%** |

**决策：暂不引入外部分词或预分词字段。** 依据：1 万篇下索引体积约 31 MB（含 FTS，可接受）、
交互检索 p95 44 ms、现有「单字 + 双字」策略对中文短语与纯英文 token 的召回均为 100%。
按 PLAN_V1.1 的约定（未达阈值不引入分词依赖），这一项到此结束。

基准同时暴露两个**与分词库无关**的真实问题，已记录待修：

1. **混合中英文写法召回为 0**：`术语A7F3`、`SQLite索引` 这类「中日韩 + 拉丁」无分隔字符串，
   现有查询构造（`core::text::build_fts_match`）无法命中（纯英文与纯中文都正常）。
   属查询表达式构造问题，不需要引入分词依赖；
2. **首次采纳大量文件耗时超线性**：3000 篇约 28 s，10000 篇 306.7 s（3.3 倍数据 → 11 倍耗时），
   FTS 重建同样从 1.5 s 涨到 24.5 s。原因是逐篇提交事务；后续应把「扫描采纳」改为分批事务。

  E2E 新增第 20 步（两个 chip 的文案与跳转）。

主题：补齐「导入 / 导出 / 布局」三块体验，并修掉影响日常使用的缺陷。

### 新增

| 能力 | 说明 |
| --- | --- |
| 导入外部文件 | 新建笔记对话框新增「导入外部文件」页签：多选 `.md` / `.markdown` / `.txt`，或选择文件夹递归导入；保留源 frontmatter 的 `id`、`title`、`tags`、创建/更新时间与未知字段；**复制语义**（源文件不变）；单文件 ≤ 5 MB、单次 ≤ 500 个；跳过原因可见 |

| 分栏拖拽 | 侧边栏（180–420px）、笔记列表（240–560px）、分屏编辑/预览比例（0.3–0.7）均可拖拽；双击复位、方向键微调 16px；拖动按帧合并更新，结束才写设置 |
| 布局记忆 | 分栏宽度、分屏比例、主题、字号、视图模式随工作区保存，切回同一知识库自动恢复 |

### 修复

| 问题 | 根因与处理 |
| --- | --- |
| 分栏「拖不动 / 一拖就贴边」 | 把手传的是像素**增量**，却直接喂给期望**绝对值**的宽度设置，第一下就被夹到最小宽度；改为值语义 API（`value/min/max/onChange/scale`） |
| 分屏比例「过渡不自然，切模式后才正常」 | 分屏容器的 `ResizeObserver` 挂在 `useEffect([editorMode])`，首次进入笔记时容器尚未挂载，观察器永不建立，拖拽按 1px = 1 换算比例而瞬间贴边；改用回调 ref，并在宽度未知时不做换算 |
| 切换笔记回到预览模式 | 视图模式此前只在拖拽分栏时才顺带持久化；现在切换即写入设置，打开/切换笔记与重启都保持一致 |
| 状态栏 `invalid args 'input' for command 'settings_update'` | Retina 屏下 `clientX` 为小数（如 320.5），前端把小数写入整数像素字段导致后端反序列化失败；前端取整、比例保留三位小数，后端数值字段改为宽容解析（四舍五入） |
| 新建笔记无法导入外部文件 | 新增导入页签（见上） |
| 列表底部出现无说明的宽度滑块 | 移除滑块，改为列表与编辑器之间的拖拽把手；「清除筛选，查看全部笔记」仅在按分类/标签筛选时出现 |
| 首页/设置页右侧大片空白 | `<main>` 为 flex 容器而页面根节点缺少 `flex-1`，内容被压到内容宽度；已修正并在宽屏下改为两列布局 |
| 导入成功后停在结果页 | 成功后自动关闭对话框并打开第一篇导入的笔记；仅在全部失败时保留原因面板 |
| 文件名标题推断错误 | `file_stem_title` 未正确剥离 `YYYYMMDD-HHmmss-` 前缀、不识别 `.txt`；目录导入时根目录被隐藏文件规则误过滤 |
| Markdown 表格导出 Word 丢表头 | pulldown-cmark 的表头不经过 `TableRow`，已在 `TableHead` 结束时收行 |
