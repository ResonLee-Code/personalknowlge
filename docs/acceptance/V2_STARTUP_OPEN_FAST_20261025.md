# 工作区打开加载优化（2026-10-25）

## 现象

软件重启后进入“正在准备工作区...”的时间明显变长。用户知识库实测为 31 篇活跃笔记、
943 个分块、约 7.8 MB，不属于大库，但旧启动路径仍同步等待：

1. 遍历并核对工作区 Markdown；
2. 探测文件系统事件能力；
3. 启动原生文件监听；
4. 最后才把工作区返回给前端。

系统繁忙或 macOS FSEvents 探测变慢时，上述步骤会一起阻塞加载页。开发日志中曾出现
5–31 秒的历史记录。

## 修复

- 已有、非空且已有持久化索引的工作区先返回界面；
- 文件监听改为后台启动，不再阻塞首屏；
- 监听启动完成后在后台补扫一次，采纳应用启动期间遗漏的外部文件变化；
- 首次创建、空目录初始化仍保留同步扫描与建索引，避免把未建库目录当成已就绪；
- 20,000 篇以上仍显示“大库已先恢复、后台核对中”提示。

实现位于 `src-tauri/src/application/workspace_service.rs`。

## 验证

- release `.app` 实测：进程启动到窗口首帧约 **0.45 s**；
- 工作区首帧日志：**73 ms**；
- 当前知识库后台补扫可采纳关闭期间新增的 Markdown；
- `workspace_flow` 20 项全部通过；
- 完整 `cargo test --offline` 通过；
- 前端 90 个测试文件、456 项测试通过；本轮新增 / 修改前端可执行语句覆盖 80.1%
  （242/302，按 diff 统计）；
- `pnpm build` 与 macOS `.app` 打包通过。

开发模式 `pnpm tauri dev` 从进程启动到 WebView 显示窗口约 5–7 秒，这是 Vite + WebKit
开发壳的启动成本；知识库本身的工作区首帧仍低于 100 ms。验收性能以打包应用为准。
